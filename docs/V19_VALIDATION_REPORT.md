# IndustrialProtocolDemo V19 验证报告

验证日期：2026-07-27

## 1. 本轮目标

V19围绕两个架构问题完成重构：

1. 恢复面向非程序人员的DataMaster主数据维护能力，删除推荐和生成代码中的成品名称、属性编号、标签、耦合和约束常量；
2. 将原有“检索式生成”替换为历史种子引导的真实参数生成，并在历史检索时自动启动后台生成。

随包成品、历史协议和模型均为虚拟演示数据，只用于验证软件和模型接口，不构成实际工程结论。

## 2. DataMaster结果

当前工作簿包含八张工作表：

- 成品信息；
- 指标定义；
- 标签字典；
- 标签规则；
- 耦合关系；
- 约束规则；
- 历史协议；
- 模型字段绑定。

当前演示数据规模：

- 成品：1个；
- 可编辑效能属性：17项；
- 标签：17项；
- 标签规则：20条；
- 耦合关系：5条；
- 约束规则：2条；
- 历史协议：96份；
- 模型字段绑定：34条。

DataMaster采用“上传—解析—校验预览—自动备份—事务提交—缓存刷新”的流程。SQLite仍为运行时权威数据源，Excel用于批量维护、迁移和交付。

本轮未增加复杂生成配置表。指标定义仅保留易于理解的“允许自动调整”开关。生成范围和联合变化由用户筛选条件、相似历史样本、显式关系和模型可行轮廓共同确定。

## 3. 无硬编码检查

对`app/`目录进行当前演示成品名称及当前属性编号扫描，未发现当前成品或属性名称出现在推荐、数据库、生成器和服务代码中。

业务特有内容仅存在于：

- DataMaster／SQLite主数据；
- 价格和效能模型产物；
- 虚拟演示数据。

新增其他成品时，不应修改Python或JavaScript代码，但必须提供与新成品匹配的DataMaster、历史协议及价格／效能模型。

## 4. 真实生成流程

用户点击历史检索后，系统立即返回历史结果，并异步执行：

1. 将用户标签、指标和模型输出条件转化为目标约束；
2. 从历史协议中选择相似且具有差异的多个种子；
3. 在局部历史样本中估计稳健尺度和连续属性相关结构；
4. 对允许自动调整的属性执行联合扰动；
5. 投影用户直接指标条件；
6. 使用模型保存的可行轮廓调整关联指标；
7. 使用DataMaster中的耦合与约束进行修复；
8. 调用效能模型、可行性模型、价格模型和分模型异常检测；
9. 严格检查标签、指标、价格、效能、效费比和可行概率条件；
10. 与历史协议和本批候选去重，并保留多样化结果。

每个生成方案均记录历史种子、实际改动属性、关系修复、可行轮廓目标和模型版本。自动测试要求生成方案至少有两个有效属性发生变化，且参数组合不得等于任何历史协议。

## 5. 双模型兼容与缺失属性

模型契约版本：3.0。

- 效能模型字段被视为完整、可编辑的成品属性集合；必填效能属性缺失时拒绝计算，不填0或工程下限；
- 价格模型拥有独立字段契约，可使用效能字段子集，也可包含价格特有字段；
- 价格特有字段只有在模型产物明确声明`training_mean`、`default`、`constant`或`zero`等策略时才允许补全；
- 价格派生特征表达式、效能硬规则和可行轮廓均来自模型产物，不写入业务代码；
- 价格与效能异常检测分别执行，允许出现一侧域内、另一侧域外的情况。

最终模型验证结果：有效，无错误，无警告。

## 8. 使用边界

当前虚拟价格和效能模型只能用于流程测试。正式接入新成品时，应同时完成：

1. 维护并提交完整DataMaster；
2. 导入完整历史协议；
3. 训练并验证价格模型；
4. 训练并验证效能／可行轮廓模型；
5. 执行`VALIDATE_MODELS.bat`；
6. 执行`RUN_FULL_PIPELINE_TEST.bat`；
7. 由业务专家验收生成方案、约束提示和模型输出。
