# 操作人员手册：当前测试数据运行与新成品更换

适用版本：`V19.6.5`

适用环境：Windows 7/10/11，64 位 Python 3.8，断网部署

本手册面向现场操作人员和成品数据配置人员。模型算法训练、专家偏好学习和正式模型确认应由模型工程师完成。

> 重要边界：数据管理中心维护的是业务成品数据，价格和效能是独立HTTP计算服务。导入、编辑、下载工作簿和切换业务数据均不调用模型，也不要求草稿与当前模型成品一致。两者不一致时只暂停推荐/计算，数据维护功能保持可用。

> 当前 `VIRTUAL_COUPLED_ACTUATOR` 的价格、协议、专家偏好和效能结论全部是虚拟测试数据，只用于系统验收，不得用于真实报价、投标或生产决策。

## 一、系统包含哪些服务

正常运行采用三个核心服务：

| 服务 | 地址 | 正式后端要求 |
|---|---|---|
| 价格预测服务 | `http://127.0.0.1:18101/docs` | `native_pickle` |

## 三、回滚当前安装

如果安装、启动、草稿校验或业务冒烟失败：

1. 关闭推荐主系统、价格服务和效能服务；
2. 找到安装时记录的 `backup_id`；
3. 执行：

```bat
ROLLBACK_PRODUCT_DELIVERY_WIN7.bat <backup_id>
```

示例：

```bat
ROLLBACK_PRODUCT_DELIVERY_WIN7.bat 20260730_213426_6B2B7050BBC5
```

回滚会恢复安装前的价格模型、效能模型和 SQLite 数据库。回滚前的当前状态还会保存在该备份目录下的 `rb_时间` 子目录中。

回滚后重新执行：

```bat
START_ALL_SERVICES_WIN7.bat
CHECK_MODEL_SERVICES.bat
```

确认旧成品和旧模型已恢复。

## 五、新成品必须统一的核心配置

新成品的三个部分必须使用同一个身份：

```text
价格模型 product_code
效能项目 product_code
业务发布包 product_code
```

成品代号规则：

```text
必须以英文字母开头；
只能包含英文字母、数字、下划线、短横线和点；
发布后不要随意修改。
```

示例：

```text
PUMP_A200
ACTUATOR-X2
VALVE.2026
```

不要使用中文成品代号或带空格的代号。中文名称填写在 `product_name`。

### 5.1 属性角色

属性可以分开维护，不要求两个模型使用完全相同的字段：

| 角色 | 说明 | 配置要求 |
|---|---|---|
| 共有属性 | 同时进入价格与效能模型 | 字段 ID、单位和业务含义必须一致 |
| 价格专用属性 | 只进入价格模型 | 在业务指标中保留，界面默认可折叠 |
| 效能专用属性 | 只进入效能模型 | 不必强行加入价格训练表 |
| 业务扩展属性 | 两个模型都不使用 | 可用于展示和业务规则，标记为 `model_bound=0` |

业务指标定义必须覆盖两个模型字段的并集。

不要因为中文名称相似就把两个不同含义的字段设成同一个 ID。

### 5.2 字段 ID、类型和单位

推荐字段 ID 使用稳定的英文小写下划线，例如：

```text
rated_thrust_n
material_grade
response_time_ms
```

支持的主要业务类型：

| 业务类型 | 用途 | 注意事项 |
|---|---|---|
| `number` | 连续数值 | 配置工程上下限和小数位 |
| `integer` | 整数/等级 | 不允许产生小数 |
| `boolean` | 是/否 | 接口可用布尔或 0/1 |
| `ip_grade` | IP 防护等级 | 推荐配置 `parser=ip_grade` |
| `enum` | 无序枚举 | 必须配置允许值；价格模型还要配置编码映射 |

系统允许效能模型把整数、布尔或 IP 等级按数值编码执行，但业务层仍保留更准确的编辑类型。

单位检查规则：

- 同一个共有字段在价格、效能和业务数据中的单位必须一致；
- `N`、`kN`、`mm`、`m` 不是同一个单位；
- 不要只修改单位文字而不重新训练模型；
- 无单位字段统一留空，不要一处填 `-`、另一处留空。

### 5.3 枚举属性

价格枚举字段必须同时配置：

```text
dtype = enum
allowed_values = 所有允许的显示值
category_mapping = 每个显示值对应的训练编码
```

示例：

```json
{
  "field_name": "material_grade",
  "dtype": "enum",
  "allowed_values": ["标准合金", "高强合金", "钛合金"],
  "category_mapping": {
    "标准合金": 0,
    "高强合金": 1,
    "钛合金": 2
  }
}
```

`category_mapping` 必须与训练数据预处理完全一致。不能为了让校验通过而临时改变编码。

效能枚举字段的允许值来自 Workbook 中的方案数据。至少应提供覆盖全部合法类别的历史方案。若该字段不参与效能生成，在“属性配置”中将“参与效能”和“参与生成”设为“否”。

## 六、制作正式新成品的推荐顺序

### 第 1 阶段：确定成品数据字典

如果已经有历史成品宽表，推荐先让系统生成数据字典草稿，而不是从空白 DataMaster 开始：

1. 打开“数据管理中心 → 待发布成品”；
2. 在“从历史成品表自动建立草稿”中填写成品代号、名称；
3. 填写缺失识别符，例如 `-1,\,/`；空单元格无需填写，系统始终识别为空；
4. 上传包含成品编号、名称、价格及全部属性的 CSV/XLSX；
5. 点击“仅分析预览”，重点检查“需要确认”的字段；
6. 点击“按推断结果建立草稿”；
7. 在草稿中逐条编辑，或下载“自动维护工作簿”，修改后再“导入到当前草稿”。

系统会把任一行曾经缺失的属性先设为非必填。列名明确表示“是否/有无”时，0/1 按有无处理；含义不明确的 0/1 按二元枚举保留，必须由数据人员确认。标签、耦合和约束可以后续分模块补充，不要求一张表建完整个项目。

自动生成的 `attr_001` 等临时字段 ID 应在正式训练前改成稳定英文 ID。数据人员既可以在“指标定义”逐条改，也可以在自动维护工作簿中批量改。

完成自动草稿后，再由数据人员和模型工程师共同确认：

1. `product_code` 和中文名称；
2. 全部属性 ID、名称、类型、单位；
3. 哪些是共有、价格专用、效能专用、业务扩展属性；
4. 枚举允许值和价格编码；
5. 工程上下限、显示精度和是否允许自动调整；
6. 标签、耦合和约束的业务含义。

数据字典确认后可分别制作两个模型。业务草稿也可以先切换并继续补充；系统不会在数据中心做统一模型校验。需要计算时，由已部署的两个HTTP服务分别判断输入是否满足各自契约。

### 第 2 阶段：制作价格原生模型包

模型工程师在可信的价格 Notebook 环境中完成训练，确保内存中存在：

```text
X_train
scaler
实际参与集成的拟合模型对象
集成权重
```

在 Notebook 最后调用：

```python
from services.price_service.export_native_price_bundle import export_from_notebook

field_metadata = {
    "训练表原列名": {
        "field_name": "稳定业务字段ID",
        "field_label": "中文名称",
        "dtype": "number",
        "unit": "单位",
        "required": True,
        "missing_policy": "reject",
        "source": "product_parameter",
    },
    "材料列": {
        "field_name": "material_grade",
        "field_label": "主体材料等级",
        "dtype": "enum",
        "unit": "",
        "allowed_values": ["标准合金", "高强合金", "钛合金"],
        "category_mapping": {"标准合金": 0, "高强合金": 1, "钛合金": 2},
        "source": "product_parameter",
    },
}

export_from_notebook(
    globals(),
    output="exports/PRODUCT_A/price_native_bundle.pkl",
    product_code="PRODUCT_A",
    product_name="正式成品A",
    model_version="price-PRODUCT_A-2026.01",
    field_metadata=field_metadata,
    ensemble_model_names=["ridge", "svr", "gbdt"],
    ensemble_weights=[0.2, 0.3, 0.5],
    strict=True,

```

必须检查同时生成的：

```text
price_native_bundle.pkl
price_native_bundle.pkl.manifest.json
```

正式模型包含什么库，目标价格服务环境就必须安装什么兼容版本。系统不会静默跳过加载失败的集成成员。

### 第 3 阶段：制作效能 Workbook 和 State

效能 Workbook 至少包含：

```text
项目信息
方案数据
属性配置
耦合关系
新技术协议
```

“项目信息”示例：

| 配置项 | 配置值 |
|---|---|
| 成品代号 | `PRODUCT_A` |
| 成品名称 | 正式成品A |

“属性配置”中的属性 ID、类型和单位应与已确认的数据字典一致。共有字段必须与价格模型一致。

专家在原 `ProjectApp` 中完成：

1. 方案数据检查；
2. 可行性证据标注；
3. 偏好比较；
4. UTA/BT 等模型训练；
5. 待复核项处理；
6. State 保存。

State 必须与当前 Workbook 的学习指纹一致。修改 Workbook 后不能继续使用旧 State。

打包效能运行包：

```bat
set EFFECT_SOURCE_ROOT=<原效能源码目录>
set EFFECT_WORKBOOK=<PRODUCT_A Workbook完整路径>
set EFFECT_STATE=<PRODUCT_A State JSON完整路径>
PACKAGE_EFFECTIVENESS_SERVICE_MODEL_WIN7.bat
```

也可以直接执行：

```bat
python -m services.effectiveness_service.package_effectiveness_runtime ^
  --source-root "<原效能源码目录>" ^
  --workbook "<PRODUCT_A Workbook>" ^
  --state "<PRODUCT_A State JSON>" ^
  --output "exports\PRODUCT_A\effectiveness_runtime"
```

输出目录必须包含 `effectiveness_runtime_manifest.json`。

### 第 4 阶段：维护七个业务模块

业务数据维护不要求先启动模型服务。启动推荐主系统后打开：

```text
http://127.0.0.1:17891/admin
```

进入“成品数据工作区”。如果前面已经从历史成品表建立草稿，直接选择该草稿继续维护；如果没有历史表，可创建任意业务 `product_code` 的空白草稿，再分别导入指标、标签、规则、耦合、约束和历史协议。空白草稿不会读取当前模型Schema。

草稿包含七个独立模块：

| 模块 | 必填重点 |
|---|---|
| 成品信息 | 只能有一条；业务代号稳定且唯一 |
| 指标定义 | 描述本业务成品属性；不要求覆盖当前模型字段并集 |
| 标签字典 | 标签 ID 唯一 |
| 标签规则 | 引用存在的标签和指标 |
| 耦合关系 | 两端指标都必须存在 |
| 约束规则 | 左右指标必须存在，或使用明确常数 |
| 历史协议 | 允许部分属性为空；已有标签引用必须有效 |

每个模块都支持三种维护方式：

- 在页面逐条新增、编辑和删除；
- 下载本模块 CSV 模板后上传；
- 上传独立 CSV/XLSX 覆盖该模块。

从历史表建立的草稿还支持第四种方式：下载整份“自动维护工作簿”，在 Excel 中维护后回导当前草稿。历史协议在数据中心逐条编辑时，各成品属性会显示为独立输入框，不要求操作人员手写 `params JSON`。

推荐操作：

1. 先维护“成品信息”和“指标定义”；
2. 再维护标签、标签规则、耦合和约束；
3. 最后导入协议数据；
4. 每个文件先点击“解析预览”；
5. 确认格式后点击“暂存到草稿”；
6. 可点击“检查业务数据（可选）”查看本地结构问题；
7. 点击“备份并切换业务数据”。

模块暂存只检查当前文件的格式和单元格类型。切换前只检查数据库无法接受的结构问题和本地跨模块引用；不比较当前价格/效能服务。因此不需要用一张总表一次构建整个项目。

草稿内容确认后，可点击“导出完整离线发布包”，得到：

```text
PRODUCT_A.iprelease.json
```

### 第 5 阶段：构建一个统一交付 ZIP

在可信的模型制作/配置机执行：

```bat
BUILD_PRODUCT_DELIVERY_WIN7.bat ^
  --price-model "exports\PRODUCT_A\price_native_bundle.pkl" ^
  --effectiveness-package "exports\PRODUCT_A\effectiveness_runtime" ^
  --business-release "exports\PRODUCT_A\PRODUCT_A.iprelease.json" ^
  --output "exports\PRODUCT_A\PRODUCT_A_delivery.zip" ^
  --delivery-version "PRODUCT_A-2026.01"
```

构建工具会统一检查：

- 三个 `product_code`；
- 价格和效能字段；
- 共有字段类型与单位；
- 业务指标是否覆盖模型字段；
- 正式后端类型；
- 包内文件 SHA-256。

成功后交给现场操作人员的文件只有：

```text
PRODUCT_A_delivery.zip
PRODUCT_A_delivery.zip.sha256
本次发布审批/验收记录
```

SHA-256 最好通过独立渠道告知现场人员。

### 第 6 阶段：断网机安装

现场人员按本文第二章的顺序执行：

```text
验包 → 停止服务 → 安装 → 打开业务草稿
→ 检查业务数据（可选） → 备份并切换业务数据
→ 启动模型服务 → 检查计算就绪度 → 冒烟检查
```

不要在断网机上重新拼接模型和业务文件，也不要直接覆盖 SQLite。

## 七、业务数据切换与计算就绪常见状态

### 成品代号不一致

现象：数据工作区提示当前业务成品与HTTP模型服务成品不同。

```text
当前业务成品与价格/效能HTTP服务暂不一致，推荐与计算暂停
```

处理：这不会阻止维护或切换。如果现场当前只是在准备新数据，无需处理；需要开始计算时，再部署该成品对应的价格和效能服务，并重启主系统或刷新就绪状态。不要为了消除提示而篡改业务代号。

### 缺少模型字段

现象：点击计算时，模型服务报告缺少输入字段。

```text
价格或效能HTTP服务缺少必填输入字段
```

处理：按该HTTP服务的Schema确认字段映射和缺失策略；可以在业务协议里补值，也可以由模型服务使用其明确声明的配置值/训练统计量。此问题不应反向阻止业务数据导入。

### 类型不一致

处理顺序：

1. 核对训练时真实类型；
2. 核对价格 `dtype/parser/category_mapping`；
3. 核对效能 Workbook 数据类型；
4. 核对业务 `value_type`。

不要仅为通过校验把枚举改成数字或把 IP 等级改成普通文本。

### 单位不一致

处理：回到模型制作端统一单位并重新打包。如果数据曾经换算，必须确认模型是否需要重新训练。

### 枚举值被拒绝

处理：核对大小写、空格、中文文字以及 `allowed_values/category_mapping`。未知枚举会被明确拒绝，不会自动映射到某个数字。

### State 与 Workbook 指纹不一致

处理：使用该 Workbook 对应的 State，或由专家重新完成学习并保存新 State。

### 推荐主系统提示模型与主数据未同步

这是安装后、激活前的正常保护状态。进入“待发布成品”校验并激活对应草稿。不要启用本地回退绕过。
